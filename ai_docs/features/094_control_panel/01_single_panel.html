094 · one graph panel

Sketches of the subtractive redesign. The layout is unchanged — editor left, rendering canvas top-right, and under it what is today the control panel. That lower half is what changes: the documents grid and the four-tab settings panel collapse into one graph canvas, the graph comes back out of the editor's tab strip, uniforms move onto the node, and Render / Share become node context items. Tokens are the real ones (gruvbox-hard, SPACE.MD = 8, THUMB_LG = 150). Nothing here is implemented; §D, §E and §B carry the three open questions.

B the node — three levels of detail

A node today is a hand-drawn card: picture, name, one port row per sampler. It gains the pass's uniforms, and it gains a level of detail driven by zoom, because a node that carries controls cannot be drawn the same way at every scale. The exact thresholds are to be tuned in the running app; what the sketch fixes is the three states and what each one drops.

far — the picture, and nothing else

The ladder is: rows → name → picture. Each step drops what has stopped being readable rather than shrinking it. The middle state's trick is that the name keeps its size while the node loses its — so a zoomed-out graph reads as labelled boxes rather than as grey rectangles with illegible captions under them. Where the two thresholds sit is a number to find by using it, not by argument.

Nineteen uniforms, nine rows tall, its own scrollbar. The node's height therefore has a ceiling, which is what keeps a heavy pass from being a wall on the canvas.

The scroll position is per pass and survives a pan or a zoom, since it belongs to the node rather than to the view.

What a row is. The uniform's existing widget, shrunk: a float is a track with its value at the right; a color is a swatch; a texture is the port it already has (its picture is on the wire's other end, so a thumbnail on the node would say it twice); a scripted uniform keeps its play/stop as a glyph where the value sits. The auto uniforms (u_time, u_resolution, …) are not rows at all — they are identical on every node, which is what the Uniforms tab's separate “auto block” was already saying.

What the node cannot hold, and where it goes. A uniform's input-type selector (slider vs. drag vs. script vs. media) and its min/max bounds are rarely-touched configuration, not live controls. They belong on the row's own right-click menu — one more context menu, no new surface.

The one real risk in this whole redesign. The graph is a hand-drawn draw-list canvas; these rows are the first interactive imgui widgets to live on it. A slider inside a node needs the overlap chain the canvas already has (set_next_item_allow_overlap on the background and on the node body, the widget submitted last) and must not start a node drag when you grab it. A scrolling region inside a node adds a second: the wheel over a node has to scroll the rows while the wheel over the canvas zooms.

The canvas half is the combo that already exists, not a new control. 093 removed the Auto | Fixed mode toggle for a reason the sketch's first draft forgot: a mode whose two positions edited different things (a ratio, a pixel pair) put a control on the row that changed meaning under it. What replaced it is canvas_choice_groups — one list grouped by aspect, each group's first row Auto, the fixed sizes of that ratio under it. Moving it onto the toolbelt is a change of host, not of shape, and there is no Mode row.

Channels keeps its one-key cycle, so the menu is a fallback rather than the only path. It leaves the canvas's top-left corner because two chips in two opposite corners is what made the image feel fenced in, and that corner is the one a wide document needs most.

Two things the first draft put here and that do not belong. Script is about the document, not its canvas — its play/stop goes on the document's own surface, which is the breadcrumb's menu (§E), beside the document's other verbs. And Render all documents is deleted outright; §E says what replaces it.

D render & share — a focused node, not a modal

The node is the target and the node is the panel. Picking Render or Share centres the view on that node, grows it to fit the controls, and dims everything else on the canvas. It reads as a modal — one thing in focus, the rest pushed back, click outside or Esc to leave — without being one: no popup, no registry row, no paused renders, and the rendering canvas above stays live the whole time.

How it is built, in the canvas's own terms. The scrim is ONE translucent rect on a new channel between _CH_OVERLAY and the focused node — not an alpha pass over every node and wire, which would be N draws and would leak through overlapping shapes. The canvas already splits its draw list into ordered channels (_CH_HALO … _CH_OVERLAY), so this is one more, and the focused node draws above it.

The scrim eats clicks, which is what makes it read as modal. Without that, a click landed on a dimmed node behind it and you would be editing two things at once. A click on the scrim leaves the mode, so click-outside-to-dismiss comes free; Esc does the same. It is the canvas's existing full-area background button, refusing every gesture (pan, band, node press) while focus is on.

The node grows in SCREEN units, not canvas units. While focused it is drawn at a fixed pixel size and ignores the zoom; its stored position and its canvas footprint never change. This matters: growing it in canvas units would make the graph's layout different after you left — Arrange would see a giant node, and wires would route around a box that is not really there. Focus is a view state, so nothing about it survives leaving it.

The camera is saved and restored. Entering stores the current pan and zoom, then animates to centre the node; leaving animates back. Without the restore, every render would leave you somewhere you did not choose. GraphViewState already holds pan/zoom and one-shot view flags like fitted, so this is three fields on a dataclass that already has this shape: the focused pass, its mode, and the saved camera.

A publish in flight holds the focus until it finishes, so progress and the artifact it produced cannot be zoomed or panned away from. That is the one case where the mode is not purely the user's to leave — the same reason today's Share panel is a fixed place.

What this settles. The overlap problem from the previous draft is gone: nothing is competing for the space, because nothing else is in focus. The target stays structural — a mode on this node renders this pass — so “render any node, not just the output” still comes free. And the width is no longer a constraint to design around: the focused node is as wide as the panel allows, so the Share accordion has room even with a second exporter.

The previews are live, and they cost nothing at rest. A document renders while the dropdown is open and not otherwise. That is a shape the app already has: the Examples popup plans its own set while it is up, one first render per frame so opening it never stalls on compiling the library at once. One difference, and it is the point — Examples replaces the normal set, this one adds to it, because the rendering canvas above stays live while you pick.

The throttle already prioritises exactly right, with no new code. plan_render_set gives current the budget first at k = ceil(cost / (budget × period)), then hands the others the remainder at one common fps. So while the dropdown is open the document you are working in keeps its rate and the four thumbnails share what is left — they slow down, it does not. Opening the list is not free, but it cannot cost you the canvas. The only wiring is that the open dropdown's documents join planned_documents; the others branch that serves them is already written and already tested.

Render all documents is deleted. It was never about the canvas — it was the switch that kept the grid's thumbnails alive, and it is a hard on/off sitting in front of a proportional mechanism that answers the same question better. With the grid gone, a non-current document has no surface to be seen on, so the render set becomes the current document, plus at most one awaiting its first render, plus the dropdown's documents while it is open. The checkbox, its app_state field and the stale-wash branch that read it all go.

What the dropdown costs us, honestly. Recognising a document by picture now takes a click. You said you work in one document at a time and do not lean on the previews, so the trade is deliberate. If it turns out wrong, a thumbnail strip pinned to the graph's bottom edge restores the at-a-glance view without undoing any of this — the dropdown stays either way, as the path that scales past a handful of documents.

The document's own verbs live on this same menu's right-click (or on a crumb's context menu): Rename, Open folder, Reset, Delete, and the script's play/stop — document_menu_items as it stands today, which already takes a document_id rather than acting on the current one.

G settled, and what is left

Settled in this round:

  • The layout stands — editor left, rendering canvas top-right, graph under it. Only the bottom half changes.
  • Documents — a dropdown on the breadcrumb, with 48x27 live previews that render only while it is open and take the throttle's remainder behind the current document. Render all documents is deleted.
  • Render / Share — modes of the node itself, not modals and not tabs. Entering one centres the view on that node, grows it in screen units and dims the rest of the canvas: contextual-modal without a popup.
  • The node — three levels of detail (rows → name → picture), and the rows scroll at 8–10 visible.
  • The canvas control — the existing grouped combo, no Mode row.

Left open:

  • The focus animation (§D) — whether entering and leaving animate the camera or cut to it, and over how long. A cut is simpler and may read as a jump; that is a running-app call.
  • The two zoom thresholds (§B) — by construction a number to find in the running app, not on paper.

Everything here is still a sketch: the code claims in §F were read off the tree today, and the spec re-checks each one before a line is written.
