084 — Projects modal, four variants

Real gruvbox tokens from theme.py, real sizes (THUMB_LG 150, ROW_HEIGHT 22, the SPACE scale), real button tiers. Each variant carries the same verbs — switch, New, Duplicate, Delete, Open other… — and differs only in how it presents them. Thumbnails are stand-ins: a project has no render of its own, which is the fact that separates these variants.

A — Tile grid (the examples gallery shape)

What the spec currently locks. Mirrors examples.py exactly, so it reads as a sibling of a surface you already know. The cost: a 150×150 square per project carrying a name and a doc count — a lot of area for two words, and the art box is empty because a project has no thumbnail.

The honest problem: the examples grid earns its thumbnails — each example looks like something. A project tile's picture is either blank or a borrowed render of one document inside it, which misrepresents a project that holds four.

B — Dense list (name, size, path) — CHOSEN

Fits the data: a project's real attributes are a name, a document count and a path — all text. Rows show the path, which is what tells radiance_cascade under the projects root apart from one opened from anywhere. The cost: plainer, and unlike anything else in the app today.

Every verb is in the one row. The first sketch put Duplicate per-row and the rest on top — two homes for verbs with no rule telling them apart. There is now ONE rule: the row acts on the selected project, whichever that is. A click SELECTS (double-click, or Enter, switches) and every verb below operates on that selection — which is also what makes Delete possible at all.

Why the path column matters: D4 unions the projects root with the open project wherever it lives. In a grid, an outside project looks identical to a rooted one; here the difference is legible at a glance — and it is exactly the confusion that put a real project in /tmp for a day.

C — List + detail pane

Verbs act on an explicit selection, and the pane has room for the facts that answer "is this the one?" — document count, last modified, full path — plus a real preview of the selected project's output document. The cost: the biggest build, and it introduces a selected-but-not-open state the other three avoid; "Switch to" becomes a button rather than a click.

Delete — armed, and what it refuses

Delete is the one verb that must not fire on a click, so it arms: the row turns red and the verb row becomes the confirm. Same shape as the document grid's cell_delete_confirm — Yes is the primary, No is standard, the red wash already carries the danger so a filled-red button would not read.

Two rules the drawing encodes. Deleting the OPEN project is disabled, not handled — it would have to tear down every GL resource, pick a replacement project and switch, all inside a confirm. Switch away first, then delete. And a deleted project MOVES to <app_data>/trash/<name>_<ms>, never rmtree: a document already deletes to its project's trash/, and a project has no enclosing project, so the app-data root is where its trash goes.

Decided — B, with one verb row

B, the dense list. A project's identity is text — name, count, path — and B is the only variant showing the path, the fact that would have made a /tmp project obvious on sight. A spends 150×150 per project on an empty picture box. C is better if a project preview is worth building. D is B with the useful columns cut.

The correction that mattered: the first draft had Duplicate per-row and the other verbs on top — two homes for verbs, no rule separating them. There is one rule now: a row click selects, the verb row acts on the selection. That also makes Delete possible, since a per-row delete-✕ on every row is how a wrong click destroys a month of work.

Spec deltas from the locked version: D2 (grid → list rows; preview_cell is no longer the primitive), D4 gains a path column, Delete comes OUT of "Out of scope" and becomes its own decision (armed confirm, disabled for the open project, moves to <app_data>/trash/), and D7's "Duplicate acts on the open project" becomes "acts on the selection" — the selection is now explicit, so it can.
