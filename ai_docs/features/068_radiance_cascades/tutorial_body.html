Radiance Cascades in ShaderBox

Build real-time 2D global illumination from nothing, one pass at a time. Build a scene of lights and walls, then paint into it with the mouse in step 1; watch light bounce, mix colour and cast soft shadows — with no ray tracing, no noise and no temporal accumulation.

This is Jason McGhee's two-part series (jason.today/gi and jason.today/rc) rewritten against this engine. Where the original drives WebGL from JavaScript, here every stage is a ShaderBox pass and the chain is graph.json. The merge is the step that is easiest to get wrong while still looking right; the explanation in step 5 says how, and oracle.py beside this file is what proves it.

Before you start. Ctrl+Shift+N makes a new document from the UV Mango starter, so it arrives with one pass called main at 1280×960. Set the canvas to 512×512 first: the Document tab's presets menu, beside the width and height fields, has 512x512 (1:1). The cascade intervals below are tuned for it. Step 1 renames the starter's pass; steps 2 to 6 each add one. Each pass step opens with a card: the pass's name, what it reads, and every target setting, with default marked where the gear's default already holds. Set the card, paste the shader, done. An input named u_<pass> wires itself to the pass of that name, so the card's reads rows are usually nothing to do. The finished thing ships as the Radiance Cascades example — open that if you get stuck, or to compare.

1paint — the scene to light

Rename the starter's pass. A new document arrives with one pass called main. Open its gear (Alt+P), type paint in the name field, click elsewhere to commit, and replace its shader with the code below. Do not delete it; steps 2 to 6 are the ones that add a pass.

{{CARD:paint}}

Bright shapes that emit and dark shapes that block: the scene everything downstream lights.

{{CODE:paint}}

Everything downstream needs something to light. One pass builds it: bright shapes that emit, dark shapes that block, and nothing else. It draws itself from scratch every frame, so it holds no state.

Why the card says 16-bit float and smooth off. An emitter is brighter than white — the warm light is vec3(4.0, 3.3, 2.0). An 8-bit target clamps that to 1.0 and every light becomes equally bright, destroying the falloff before it starts. And smooth makes reads blend between texels, which would smear the crisp edge that tells the next pass exactly where a wall is.

The alpha channel is the convention everything downstream keys off: alpha 1 means "something solid is here", and RGB is what it emits. A wall is solid and black; a light is solid and bright. A ray stops at the first solid texel it reaches — so a black one casts a shadow and a bright one is where light comes from.

Paint it with the mouse

The shipped example draws its scene analytically and ships no script, so an exported video is the same every time. Everything below is yours to add on top.

First the uniforms. Add three declarations to paint.frag.glsl, beside the ones already there: 

uniform vec2 u_brush;        // where the cursor is, 0..1
uniform vec2 u_brush_prev;   // where it was last frame
uniform float u_brush_down;  // 1 while the left button is held

Then, inside main(), immediately before the final fs_color = vec4(0.0);: 

    // Distance to the SEGMENT from last frame's cursor to this one, so a fast drag paints a
    // continuous stroke instead of one disc per frame.
    vec2 ab = u_brush - u_brush_prev;
    float h = clamp(dot(p - u_brush_prev, ab) / max(dot(ab, ab), 1e-6), 0.0, 1.0);
    if (u_brush_down > 0.5 && length(p - (u_brush_prev + ab * h)) < 0.02) {
        fs_color = vec4(4.0, 3.3, 2.0, 1.0);
        return;
    }

Now the script that feeds them. Press Alt+R: the document's scripts/script.py is written for you and opens in a tab, with a stub in it. Paste this over the stub: 

from shaderbox.scripting import ScriptBehavior, Ctx, Vec2


class Brush(ScriptBehavior):
    """Paint into the scene with the left mouse button."""

    def update(self, ctx: Ctx) -> dict:
        return {
            "paint": {
                "u_brush": Vec2(ctx.mouse.x, ctx.mouse.y),
                "u_brush_prev": Vec2(ctx.mouse.prev_x, ctx.mouse.prev_y),
                "u_brush_down": 1.0 if ctx.mouse.down else 0.0,
            },
        }

The key is "paint", not the output pass: a script addresses a pass by NAME, so this one drives paint while you are looking at composite. The value under it is a dict, and that is what makes it a pass block — one pass only. A bare "u_brush": … at the top level would instead broadcast to every pass declaring u_brush, which here is only paint and would work too; the block form is the one that scales.

Two smaller things. ctx.mouse.down is a bool and the uniform is a float, so the script converts. And prev_x / prev_y come from the engine rather than from self: a script keeping its own previous position would miss the re-entry reset the engine performs, so a cursor that left the canvas and came back would draw a line across the gap.

Hold the left button over the canvas and it paints; hover with no button and nothing happens; a fast drag leaves a continuous line rather than spaced discs.

There is nothing to clear. paint redraws from scratch every frame, so releasing the button leaves the analytic scene and the next frame has no brush in it. F6 (Clear canvas) and its Clear button appear only once a pass reads itself, which is why they belong to the persistent-canvas suggestion in Things to try rather than to this step.

Naive global illumination

Nothing to build here. This is the idea the cascade pass is an optimisation of; the shipped example has no naive pass.

Here is the whole idea, in its simplest correct form. For every pixel, fire rays in a circle. Walk each ray forward until it hits something solid. Add up what the rays found, divide by how many you fired. That average is the light arriving at that pixel. 

vec4 raymarch() {
    vec4 light = texture(u_paint, vs_uv);
    if (light.a > 0.1) return light;      // this pixel IS a light; nothing to gather

    float one_over = 1.0 / float(RAY_COUNT);
    float noise = rand(vs_uv);            // jitter, or you get banding
    vec4 radiance = vec4(0.0);

    for (int i = 0; i < RAY_COUNT; i++) {
        float angle = TAU * one_over * (float(i) + noise);
        vec2 dir = vec2(cos(angle), -sin(angle)) / u_resolution;
        vec2 uv = vs_uv + dir;

        for (int step = 0; step < MAX_STEPS; step++) {
            if (uv.x < 0.0 || uv.x > 1.0 || uv.y < 0.0 || uv.y > 1.0) break;
            vec4 hit = texture(u_paint, uv);
            if (hit.a > 0.1) { radiance += hit; break; }
            uv += dir;                    // one texel at a time
        }
    }
    return radiance * one_over;
}

This works. It also crawls: each ray steps one texel at a time, so a ray crossing a 512-wide canvas takes 512 texture reads. At 32 rays per pixel that is 16 000 reads per pixel per frame, and 32 rays is still few enough to look noisy.

The original article reaches for temporal accumulation here — jitter the noise by time and blend 90% of the previous frame — which trades noise for smearing. Worth knowing, because radiance cascades needs none of it: its ray directions are deterministic, so there is no noise to hide.

The next three passes exist to fix the crawl. The insight: if a ray knew how far away the nearest solid thing was, it could jump that whole distance in one step, because nothing can possibly be hit before then.

2seed — positions, not distances

Add a pass called seed (Alt+A).

{{CARD:seed}}

Every solid texel stores its own coordinate; every empty one stores nothing.

{{CODE:seed}}

We want, for every texel, the distance to the nearest solid texel. That is built in two moves: first every texel learns the position of its nearest solid texel, then distance is just subtraction. A solid texel stores its own UV. An empty one stores (0,0), which everything downstream reads as "nothing known here".

Why the card says 32-bit float. It stores coordinates, not colours. At 8-bit a UV quantizes to 1/255 and the distance field comes out visibly blocky; at 16-bit it is subtly wrong. This is the one pass where f4 genuinely earns its cost.

3jfa — the jump flood

Add a pass called jfa, as before.

{{CARD:jfa}}

Every texel — not just the solid ones — holds the coordinate of the nearest solid texel.

{{CODE:jfa}}

Now spread those coordinates outward until every texel knows the nearest one. The naive way is to check every texel against every solid texel — O(n²), hopeless. The jump flood algorithm does it in log₂(size) passes. Each pass looks at 8 neighbours at a given offset and keeps the nearest seed found. The offset halves each pass: first 256 texels away, then 128, 64, down to 1. Big jumps carry coordinates across the canvas; small jumps refine the answer locally.

The offset is derived from the canvas, not from the run count: run i jumps exp2(ceil(log2(max side)) - 1 - i) texels, so the chain is complete after ceil(log2(max side)) runs and any run past that has nothing left to spread and copies its input forward. The card says 12, which is ceil(log2(4096)) and therefore covers every canvas the app can make. One shader, twelve runs.

Why the shader reads two different inputs. An iterated pass that read only itself would never receive anything — run 0 would sample an empty texture and the chain would flood nothing. So run 0 reads the seed, and every later run reads what the run before it wrote. Any iterated chain needs a seam like this to start it.
The engine hands over the index, not the offset. u_pass_iteration says which run this is; turning that into a halving offset is the algorithm's business, not the engine's. That is why there is no u_jfa_offset — the engine stays a general tool and this stays one line of shader.
Resize freely. The offset formula follows the canvas, so the run count covers every canvas the app can make: 12 runs are ceil(log2(4096)), and 4096 is the largest side the width and height fields accept. Raise it only if you raise that limit. A short chain would still render, just with a subtly wrong distance field and no error anywhere, which is why the number covers the whole range rather than the size you happen to be using.

4df — one line of real work

Add a pass called df, as before.

{{CARD:df}}

Brightness is distance: how far a ray standing here can jump in any direction and hit nothing.

{{CODE:df}}

One line of real work: the nearest solid coordinate minus this texel's own, and the length of that. A texel that learned no coordinate at all reports the farthest distance there is, which is what lets a ray in empty space clear the canvas in one jump.

Sphere marching

Nothing to build here. This is the loop the cascade pass runs; you will paste it as part of cascade.frag.glsl in step 5, in its march function. Compare it against the naive walk above. 

for (int step = 0; step < MAX_STEPS; step++) {
    float dist = texture(u_df, uv).r;
    uv += dir * dist;                        // jump the whole safe distance
    if (uv.x < 0.0 || uv.x > 1.0 || uv.y < 0.0 || uv.y > 1.0) break;
    if (dist < EPS) { radiance += texture(u_paint, uv); break; }
}

Same picture, roughly 20× fewer steps. A ray crossing open space clears it in two or three jumps instead of five hundred. This is sphere marching, and it is what makes the rest affordable.

At this point the algorithm is correct and it is pretty — and it still costs rays × steps per pixel, so smooth results need hundreds of rays. Everything from here is about getting the same quality for about 8 rays per pixel.

The cascade idea

Nothing to build here. This is the observation the whole technique rests on, called the penumbra hypothesis, and the layout it forces.

Light that is far away needs many directions but few positions — it changes slowly across space. Light that is close needs the opposite: few directions, but you must know exactly where you are. Spatial resolution and angular resolution trade off against distance, in opposite directions.

Naive GI ignores this and pays full price everywhere: every pixel, every direction, all distances. Cascades split the work into levels, each handling one distance band:

LevelProbesDirectionsCovers
0every pixel40 → 0.012
1every 2nd pixel160.012 → 0.060
2every 4th640.060 → 0.252
3every 8th2560.252 → 1.020
4every 16th10241.020 → 4.092
5every 32nd40964.092 → 16.38

Each level has 4× the directions and ¼ the probes of the one below, so every level costs the same. The intervals tile exactly — each starts where the last ended — and by level 5 the reach exceeds the canvas diagonal.

How a level is packed is the part that confuses everyone, so read it slowly. Every level writes into the same full-size texture. There is no per-level resolution. At level c the probes sit sp = 2^c texels apart, and the sp × sp block of texels belonging to a probe stores that probe's directions — one direction per texel. A coarse level has few probes each holding many directions; level 0 is one probe per pixel holding 4. The texture never changes shape; only the meaning of its texels does.

5cascade — the cascade stack

Add a pass called cascade, as before. This is the pass the whole feature is for, and it is the only one longer than a screen. Paste it whole and read the explanation underneath.

{{CARD:cascade}}

The light itself: raw unclamped radiance at every pixel, computed coarse to fine.

{{CODE:cascade}}

Packing

The block near the top that computes sp, probe, slot and si is the packing described above, in code: sp is the probe spacing in texels at this level, probe is which probe this texel belongs to, slot is which direction within that probe, and probe_uv is where that probe actually sits on the canvas. Every texel of the target is one direction of one probe, and these four lines are what say which.

The runs go coarse → fine while the engine counts up, so the shader flips the index: level = u_pass_iterations - 1.0 - u_pass_iteration. Run 0 computes the coarsest level, which has nothing above it; every later run merges the one before.

The march

The march function is the sphere-marching loop from the interlude above, bounded to this level's own interval: it starts at t0 and gives up at t1 rather than walking to the canvas edge. That bound is what makes every level cost the same, and it is the whole reason the stack is affordable.

The merge

A ray marches its own interval. If it hits something, that is the answer. If it reaches the end of its shell having hit nothing, it asks the level above what lies further out — and that level has already asked the one above it, so one lookup carries the whole remaining distance.

This is the single easiest thing in the pipeline to get wrong, and the failure is invisible: address the upper slot with a slot dimension in one component and a probe spacing in the other and it still renders convincing shadows while being 30% off. Both components must use the same quantity — usp in the code above.

The four taps are a bilinear blend done by hand, and the target stays unsmoothed for the same reason. Neighbouring texels here are different directions of the same probe, not neighbouring positions, so hardware filtering would blend unrelated angles. The four taps sample the same slot in four neighbouring probes, which is the quantity you actually want.

The clamp is not decoration either: without it a probe at the canvas edge reads across to the far side and light leaks from one wall to the other.

6composite — what you look at

Add a pass called composite, as before, and set it as the document's output.

{{CARD:composite}}

The finished image: tonemapped light with the scene drawn back on top, in sRGB.

{{CODE:composite}}

Three things happen here. Reinhard maps unbounded light into 0–1 without clipping highlights to flat white. Drawing the scene back on top keeps walls reading as solid — without it they get lit by the light in front of them and stop looking like occluders. And the sRGB conversion is mandatory: skip it and everything looks muddy and the falloff is crushed.

Verifying it

Nothing to build here. This is how you find out whether what you built is right.

A good-looking render proves nothing. This repo's own earlier attempt at this algorithm rendered convincing shadows, beat brute force 16:1, and was 30% wrong — every one of its 1364 merge directions read the wrong slot. It was believed because the picture looked right. Check the number.

ai_docs/features/068_radiance_cascades/oracle.py runs this same algorithm on an analytic scene and compares it against brute force. Two numbers, because they say different things: 

  2 cascades (reach 0.060,  13881 bounced texels): ratio 1.0090, relMAE  9.57%
  3 cascades (reach 0.252, 116572 bounced texels): ratio 1.0102, relMAE  4.39%
  4 cascades (reach 1.020, 239331 bounced texels): ratio 1.0134, relMAE  3.65%

3.65% at full depth against a converged 16 384-ray reference, scored over bounced light only, with each depth measured against a reference marched to that depth's own reach. The error falls as the stack deepens, which is the shape you want. That matches the 4.5% an earlier corrected implementation of this algorithm measured — and the number means something because the gate is mutation-tested: disabling the merge scores 98%, and a transposed slot address scores 30%, almost exactly the 30.3% that earlier broken version measured for that same bug.

Two ways to measure this wrong, both of which produced confident numbers here. Testing emission for "strictly inside a surface" while the marcher reports a hit slightly outside one loses nearly all direct light: the reference goes dark, and the apparent "21% overshoot" it produced was entirely a bug in the measuring harness, not the algorithm. And scoring the whole frame rather than only the bounced texels measures the emitters — which both methods write identically — so a stack computing no global illumination at all scored inside the passing band.
Match your comparison or it measures nothing. A stack of n levels resolves 4ⁿ directions and marches only as far as its own intervals reach. Compare it against a coarser, shorter reference and you get a large "error" that is entirely the reference — a 580% figure that cost real time here was exactly that.

Things to try

  • Set cascade's runs to 1, 2, 3… and watch the light reach further each time.
  • Point the document's output at df or jfa to see any stage directly.
  • Turn smooth on for cascade and watch the merge break in an interesting way.
  • Raise jfa's runs above 12 and nothing changes: the extra runs copy their input forward. Lower it to 4 and the field goes blocky at range, which is the same experiment from the other side.
  • Wire paint's u_prev to paint itself and stop clearing every frame, so the brush accumulates. Now F6 (Clear canvas) and its Clear button have something to do.
