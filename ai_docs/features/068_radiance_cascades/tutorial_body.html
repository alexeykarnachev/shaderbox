Radiance Cascades in ShaderBox

Build real-time 2D global illumination from nothing, one pass at a time. Paint light and walls with the mouse; watch light bounce, mix colour and cast soft shadows — with no ray tracing, no noise and no temporal accumulation.

This is Jason McGhee's two-part series (jason.today/gi and jason.today/rc) rewritten against this engine. Where the original drives WebGL from JavaScript, here every stage is a ShaderBox pass and the chain is graph.json. Two corrections to the published code are marked CORRECTION where they come up — both were verified numerically, not by eye.

Before you start. Make a new document (Ctrl+N), open the Passes strip in the Document tab, and give yourself a 512×512 canvas. Each step below adds one pass: click add pass, name it, paste the shader, then open its gear to wire its inputs and set its target. The finished thing ships as the Radiance Cascades example — open that if you get stuck, or to compare.

1A canvas you can draw on

Everything downstream needs a scene to light. Rather than hard-coding shapes, we make a canvas that remembers — you paint into it and it keeps what you painted.

A fragment shader has no memory: it runs fresh every frame and forgets everything. The way you give it memory is to let it read its own output from the previous frame. In ShaderBox you wire a pass's sampler input to itself; the engine calls this feedback and keeps a second texture behind the scenes, so you read last frame while writing this one.

Add a pass called paint:

#version 460 core

in vec2 vs_uv;
out vec4 fs_color;

uniform sampler2D u_prev;
uniform vec4 u_brush;            // xy = cursor UV, z = radius, w = 0 off / 1 painting
uniform vec3 u_brush_color;
uniform float u_brush_emissive;  // 1 = a light, 0 = a wall

// Squared distance from p to the segment a-b. Squared so there is no sqrt in the hot path.
float sd_seg_sq(vec2 p, vec2 a, vec2 b) {
    vec2 pa = p - a, ba = b - a;
    float len_sq = max(dot(ba, ba), 1e-9);
    float t = clamp(dot(pa, ba) / len_sq, 0.0, 1.0);
    vec2 d = pa - ba * t;
    return dot(d, d);
}

void main() {
    vec4 current = texture(u_prev, vs_uv);
    if (u_brush.w > 0.5) {
        float r = u_brush.z;
        if (sd_seg_sq(vs_uv, u_brush.xy, u_brush.xy) <= r * r) {
            current = vec4(u_brush_color * u_brush_emissive, 1.0);
        }
    }
    fs_color = current;
}

In the pass's settings: wire u_prev to paint (itself), set the format to 16-bit float, and turn smooth off.

Why 16-bit float, and why not smooth. An emitter is brighter than white — the warm light below is vec3(4.0, 3.3, 2.0). An 8-bit target clamps that to 1.0 and every light becomes equally bright, destroying the falloff before it starts. And smooth makes reads blend between texels, which would smear the crisp edge that tells the next pass exactly where a wall is.

The alpha channel is the important convention: alpha 1 means "something solid is here". RGB is what it emits. A wall is solid and black; a light is solid and bright. Every later pass keys off that single bit.

The cursor comes from a script

A shader can't read the mouse. In ShaderBox, a script can — it gets a ctx each frame and returns uniform values. Add scripts/script.py to the document: 

import math
from shaderbox.scripting import Ctx, ScriptBehavior, Vec3, Vec4


class Behavior(ScriptBehavior):
    def __init__(self) -> None:
        self.last: tuple[float, float] | None = None

    def update(self, ctx: Ctx) -> dict[str, object]:
        x, y = ctx.mouse.x, ctx.mouse.y
        moved = self.last is not None and math.dist((x, y), self.last) > 0.002
        self.last = (x, y)
        return {
            "u_brush": Vec4(x, y, 0.02, 1.0 if moved else 0.0),
            "u_brush_color": Vec3(4.0, 3.0, 1.6),
            "u_brush_emissive": 1.0,
        }
ctx.mouse has position but no buttons. So there is no click to gate on: the brush paints whenever the cursor moves. The distance threshold matters — without it a resting cursor burns a permanent dot into a canvas that never forgets.

;2Naive global illumination

Here is the whole idea, in its simplest correct form. For every pixel, fire rays in a circle. Walk each ray forward until it hits something solid. Add up what the rays found, divide by how many you fired. That average is the light arriving at that pixel. 

vec4 raymarch() {
    vec4 light = texture(u_scene, vs_uv);
    if (light.a > 0.1) return light;      // this pixel IS a light; nothing to gather

    float one_over = 1.0 / float(RAY_COUNT);
    float noise = rand(vs_uv);            // jitter, or you get banding
    vec4 radiance = vec4(0.0);

    for (int i = 0; i < RAY_COUNT; i++) {
        float angle = TAU * one_over * (float(i) + noise);
        vec2 dir = vec2(cos(angle), -sin(angle)) / u_resolution;
        vec2 uv = vs_uv + dir;

        for (int step = 0; step < MAX_STEPS; step++) {
            if (uv.x < 0.0 || uv.x > 1.0 || uv.y < 0.0 || uv.y > 1.0) break;
            vec4 hit = texture(u_scene, uv);
            if (hit.a > 0.1) { radiance += hit; break; }
            uv += dir;                    // one texel at a time
        }
    }
    return radiance * one_over;
}

This works. It also crawls: each ray steps one texel at a time, so a ray crossing a 512-wide canvas takes 512 texture reads. At 32 rays per pixel that is 16 000 reads per pixel per frame, and 32 rays is still few enough to look noisy.

The original article reaches for temporal accumulation here — jitter the noise by time and blend 90% of the previous frame — which trades noise for smearing. Worth knowing, because radiance cascades needs none of it: its ray directions are deterministic, so there is no noise to hide. If you build this stage, give it a persist target and blend with u_prev; then delete it happily at step 7.

The next three passes exist to fix the crawl. The insight: if a ray knew how far away the nearest solid thing was, it could jump that whole distance in one step, because nothing can possibly be hit before then.

3The seed pass

We want, for every texel, the distance to the nearest solid texel. That is built in two moves: first every texel learns the position of its nearest solid texel, then distance is just subtraction.

This pass writes the starting state. Add seed, wired to paint:

#version 460 core

in vec2 vs_uv;
out vec4 fs_color;
uniform sampler2D u_scene;

void main() {
    float alpha = texture(u_scene, vs_uv).a;
    fs_color = vec4(vs_uv * alpha, 0.0, 1.0);
}

A solid texel stores its own UV. An empty one stores (0,0), which everything downstream reads as "nothing known here".

Set this target to 32-bit float. It stores coordinates, not colours. At 8-bit a UV quantizes to 1/255 and the distance field comes out visibly blocky; at 16-bit it is subtly wrong. This is the one pass where f4 genuinely earns its cost.

4The jump flood

Now spread those coordinates outward until every texel knows the nearest one. The naive way is to check every texel against every solid texel — O(n²), hopeless. The jump flood algorithm does it in log₂(size) passes.

Each pass looks at 8 neighbours at a given offset and keeps the nearest seed found. The offset halves each pass: first 256 texels away, then 128, 64, down to 1. Big jumps carry coordinates across the canvas; small jumps refine the answer locally.

At 512×512 that is ceil(log₂(512)) = 9 passes — and this is exactly what ShaderBox's Runs per frame is for. One shader, nine runs. 

#version 460 core

in vec2 vs_uv;
out vec4 fs_color;

uniform sampler2D u_prev;
uniform sampler2D u_seed;
uniform float u_pass_iteration;    // which run this is, 0-based
uniform float u_pass_iterations;   // how many runs in total
uniform vec2 u_resolution;

void main() {
    float offset = pow(2.0, u_pass_iterations - u_pass_iteration - 1.0);
    bool first = u_pass_iteration < 0.5;

    vec4 nearest = vec4(0.0);
    float nearest_dist = 1e9;

    for (float y = -1.0; y <= 1.0; y += 1.0) {
        for (float x = -1.0; x <= 1.0; x += 1.0) {
            vec2 uv = vs_uv + vec2(x, y) * offset / u_resolution;
            if (uv.x < 0.0 || uv.x > 1.0 || uv.y < 0.0 || uv.y > 1.0) continue;

            vec4 sampled = first ? texture(u_seed, uv) : texture(u_prev, uv);
            if (sampled.x == 0.0 && sampled.y == 0.0) continue;

            vec2 diff = sampled.xy - vs_uv;
            float d = dot(diff, diff);
            if (d < nearest_dist) { nearest_dist = d; nearest = sampled; }
        }
    }
    fs_color = nearest;
}

Wire u_seed → seed, u_prev → jfa (itself), format 32-bit float, smooth off, and set Runs per frame to 9.

Why the shader reads two different inputs. An iterated pass that read only itself would never receive anything — run 0 would sample an empty texture and the chain would flood nothing. So run 0 reads the seed, and every later run reads what the run before it wrote. Any iterated chain needs a seam like this to start it.
The engine hands over the index, not the offset. u_pass_iteration says which run this is; turning that into a halving offset is the algorithm's business, not the engine's. That is why there is no u_jfa_offset — the engine stays a general tool and this stays one line of shader.
Resize changes the answer. 9 runs spans 512px; a 1024px canvas needs 10. Come up short and it still renders — just with a subtly wrong distance field and no error anywhere. The pass settings panel warns you when the count no longer reaches, because this failure is invisible.

5The distance field

One line of real work. Add df, wired to jfa:

#version 460 core

in vec2 vs_uv;
out vec4 fs_color;
uniform sampler2D u_jfa;

void main() {
    vec2 nearest = texture(u_jfa, vs_uv).xy;
    float d = (nearest.x == 0.0 && nearest.y == 0.0)
        ? 1.0                                    // nothing solid anywhere: as far as it gets
        : distance(vs_uv, nearest);
    fs_color = vec4(vec3(clamp(d, 0.0, 1.0)), 1.0);
}

6Sphere marching

Now the payoff. Replace the naive inner loop's fixed step with a jump by the distance field: 

for (int step = 0; step < MAX_STEPS; step++) {
    float dist = texture(u_df, uv).r;
    uv += dir * dist;                        // jump the whole safe distance
    if (uv.x < 0.0 || uv.x > 1.0 || uv.y < 0.0 || uv.y > 1.0) break;
    if (dist < EPS) { radiance += texture(u_scene, uv); break; }
}

Same picture, roughly 20× fewer steps. A ray crossing open space clears it in two or three jumps instead of five hundred. This is sphere marching, and it is what makes the rest affordable.

At this point you have working global illumination. It is correct and it is pretty — and it still costs rays × steps per pixel, so smooth results need hundreds of rays. Everything from here is about getting the same quality for about 8 rays per pixel.

7Radiance cascades

The observation the whole technique rests on, called the penumbra hypothesis:

Light that is far away needs many directions but few positions — it changes slowly across space. Light that is close needs the opposite: few directions, but you must know exactly where you are. Spatial resolution and angular resolution trade off against distance, in opposite directions.

Naive GI ignores this and pays full price everywhere: every pixel, every direction, all distances. Cascades split the work into levels, each handling one distance band:

LevelProbesDirectionsCovers
0every pixel40 → 0.012
1every 2nd pixel160.012 → 0.060
2every 4th640.060 → 0.252
3every 8th2560.252 → 1.020
4every 16th10241.020 → 4.092
5every 32nd40964.092 → 16.38

Each level has 4× the directions and ¼ the probes of the one below, so every level costs the same. The intervals tile exactly — each starts where the last ended — and by level 5 the reach exceeds the canvas diagonal.

How a level is packed

This is the part that confuses everyone, so read it slowly. Every level writes into the same full-size texture. There is no per-level resolution.

At level c the probes sit sp = 2^c texels apart, and the sp × sp block of texels belonging to a probe stores that probe's directions — one direction per texel. A coarse level has few probes each holding many directions; level 0 is one probe per pixel holding 4. The texture never changes shape; only the meaning of its texels does. 

float sp    = exp2(level);              // probe spacing in texels
float rays  = 4.0 * sp * sp;            // directions at this level
vec2  co    = floor(vs_uv * u_resolution);
vec2  probe = floor(co / sp);           // which probe this texel belongs to
vec2  slot  = mod(co, sp);              // which direction within that probe
float si    = slot.x + slot.y * sp;
vec2  probe_uv = (probe + 0.5) * sp / u_resolution;

8The merge

A ray marches its own interval. If it hits something, that is the answer. If it reaches the end of its shell having hit nothing, it asks the level above what lies further out — and that level has already asked the one above it, so one lookup carries the whole remaining distance.

CORRECTION The published snippet is wrong here, and it is the single easiest thing in this entire pipeline to get wrong. The article computes the upper slot as vec2(mod(index, sqrtBase), floor(index / upperSpacing)) — mixing a slot dimension with a probe spacing. Both components must use the same quantity. Get this wrong and it still renders convincing shadows while being 30% off; that exact bug shipped once in this repo's own research and took a numerical comparison to catch. 
float usp = sp * 2.0;                          // the level above is spaced twice as wide
vec2  upf = probe_uv * u_resolution / usp - 0.5;

for (float k = 0.0; k < 4.0; k++) {
    float idx = si * 4.0 + k;
    float a   = TAU * (idx + 0.5) / rays;
    vec4  hit = march(probe_uv, vec2(cos(a), sin(a)), t0, t1);
    vec3  r   = hit.rgb;

    if (hit.a < 0.5 && level < u_pass_iterations - 1.0) {
        // The level above wrote the MEAN of its 4 sub-directions into each slot, so its slot
        // `idx` already holds exactly this ray's angular children. One tap, and BOTH
        // components of the address use usp.
        vec2 uslot = vec2(mod(idx, usp), floor(idx / usp));
        vec2 base = floor(upf), fr = fract(upf);
        vec2 lim  = vec2(u_resolution / usp - 1.0);
        vec2 c00 = clamp(base,               vec2(0.0), lim) * usp + uslot + 0.5;
        vec2 c10 = clamp(base + vec2(1, 0),  vec2(0.0), lim) * usp + uslot + 0.5;
        vec2 c01 = clamp(base + vec2(0, 1),  vec2(0.0), lim) * usp + uslot + 0.5;
        vec2 c11 = clamp(base + vec2(1, 1),  vec2(0.0), lim) * usp + uslot + 0.5;
        r += mix(mix(texture(u_prev, c00 / u_resolution).rgb,
                     texture(u_prev, c10 / u_resolution).rgb, fr.x),
                 mix(texture(u_prev, c01 / u_resolution).rgb,
                     texture(u_prev, c11 / u_resolution).rgb, fr.x), fr.y);
    }
    acc += r;
}
fs_color = vec4(acc * 0.25, 1.0);
CORRECTION Do the bilinear blend by hand, and keep the target unsmoothed. The article leans on the GPU's linear filter for "nearly free smoothing". That is wrong at this texture layout: neighbouring texels are different directions of the same probe, not neighbouring positions, so hardware filtering blends unrelated angles. The four taps above sample the same slot in four neighbouring probes, which is the quantity you actually want. Leave smooth off on this target.

The clamp is not decoration either: without it a probe at the canvas edge reads across to the far side and light leaks from one wall to the other.

Wire u_scene → paint, u_df → df, u_prev → cascade (itself); format 16-bit float, smooth off, Runs per frame = 6.

Runs go coarse → fine, but the engine counts up. So the shader flips the index: float level = u_pass_iterations - 1.0 - u_pass_iteration;. Run 0 computes level 5, which has nothing above it; every later run merges the one before.

9Composite

#version 460 core

in vec2 vs_uv;
out vec4 fs_color;

uniform sampler2D u_light;
uniform sampler2D u_scene;
uniform float u_exposure = 0.35;

void main() {
    vec3 light  = texture(u_light, vs_uv).rgb * u_exposure;
    vec3 mapped = light / (1.0 + light);          // Reinhard: any brightness into 0-1
    vec4 scene  = texture(u_scene, vs_uv);
    vec3 rgb    = mix(mapped, scene.rgb / (1.0 + scene.rgb), scene.a);
    fs_color    = vec4(pow(max(rgb, 0.0), vec3(1.0 / 2.2)), 1.0);   // linear -> sRGB
}

Three things happen here. Reinhard maps unbounded light into 0–1 without clipping highlights to flat white. Drawing the scene back on top keeps walls reading as solid — without it they get lit by the light in front of them and stop looking like occluders. And the sRGB conversion is mandatory: skip it and everything looks muddy and the falloff is crushed.

Wire u_light → cascade, u_scene → paint, format 8-bit (this is a final image), smooth on. Set it as the document's output.

10Verifying it

A good-looking render proves nothing. This repo's own earlier attempt at this algorithm rendered convincing shadows, beat brute force 16:1, and was 30% wrong — every one of its 1364 merge directions read the wrong slot. It was believed because the picture looked right. Check the number.

ai_docs/features/068_radiance_cascades/oracle.py runs this same algorithm on an analytic scene and compares it against brute force. Two numbers, because they say different things: 

merge off, level 0 alone vs 4 rays:   1.0000
merge on,  2 cascades vs   16 rays:   1.0432
merge on,  3 cascades vs   64 rays:   1.1241
merge on,  4 cascades vs  256 rays:   1.2087

The first isolates the marching and interval arithmetic with the merge switched off — it is exact, and it is what a porting mistake would move. The second shows a real ~21% energy overshoot that grows per merge hop and then saturates: the near-field over-sampling that bilinear probe interpolation introduces, the same family as the ringing. It is not a wiring bug, which you can prove by turning the merge off and watching it return to 1.0000.

Match your comparison or it measures nothing. A 6-level stack resolves 4⁶ directions and marches 16.4 UV. Compare it against 1024 rays capped at 2.0 and you get a 580% "error" that is entirely the reference being coarser and shorter — that misread cost real time here. Level n equals 4ⁿ rays over the stack's own reach.

Things to try

  • Set cascade's runs to 1, 2, 3… and watch the light reach further each time.
  • Set jfa's runs to 4 and look at df — the field goes blocky at range.
  • Point the document's output at df or jfa to see any stage directly.
  • Turn smooth on for cascade and watch the merge break in an interesting way.
  • Resize the canvas to 1024 and read the warning the pass settings give you.
