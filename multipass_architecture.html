Multi-pass architecture

A sketch for review, not a spec. The question it answers: what replaces “a node is one shader”.

The problem in one picture

The survey in 063/11_playground_survey.md is unambiguous: one editable unit per render target is what Shadertoy (tabs), KodeLife (tree nodes), SHADERed (<pass>), TouchDesigner and VVVV (graph nodes), vscode-shader-toy and shadertoy-local (files) all do. Only glslViewer packs passes into one file — and it exposes no per-pass size, format, filter or wrap at all.

The naming collision, which is the actual handicap

“Node” currently does two jobs — the document you open and save, and the unit of rendering. Every attempt to add a second render unit has been pushed back by that collision: passes could not be nodes, so they became functions in a file.

Both words are placeholders — naming is question Q1 below. What matters here is the split, not the labels.

The DAG, and what a pass may read

How a pass names what it reads — the seam

With one file per pass, a pass declares an ordinary uniform sampler2D u_src; and something must say which pass fills it. Two candidates, and this is question Q2.

A — wired in graph.json app-written

The pass file is a plain shader; the graph says blur.u_src ← bright. Rename a pass and the wiring updates; a shader is portable on its own.

Cost: two places to look to understand one effect.

B — named by convention in the code

A sampler called u_pass_bright reads the pass named bright. The wiring is visible where it is used, and cannot desync.

Cost: renaming a pass breaks every shader that reads it.

The survey splits: Shadertoy and SHADERed wire outside the source; vscode-shader-toy and shadertoy-local name the file in the source. Your standing rule — declare by name, never by comment — rules out a third option (a rider comment) but does not settle A vs B, since both are real declarations.

Open questions — yours to settle

Q1 — naming. What is the container called, and what is a pass called? “Node” must stop meaning the document. It could become the pass (your suggestion), or retire entirely. This decides ~910 mentions and the on-disk nodes/ directory, so it is worth settling before any code.

Q2 — the wiring seam. A or B above. Wired in the graph file, or named by convention in the sampler.

Q3 — shared uniforms. Eight cascade passes want one u_ray_count. Options: one slider per pass (isolated, tedious); an explicit shared block the passes include; or the graph binds one value to several passes. Shadertoy sidesteps this by having no per-pass uniforms at all.

Q4 — migration. The project rule is no migration code, hand-fix the sandbox instead. There are two multi-pass nodes on disk (the shipped example and projects/dev) and the rest are single-shader. Does a plain single-shader document stay exactly as it is on disk, or does everything move to the new layout?

Q5 — scope of the revert. Revert the design commits and keep the seven bug fixes, or keep 064 on disk as a reference and build the new feature beside it? My recommendation is the former — two live step systems would be worse than either.
