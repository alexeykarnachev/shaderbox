# Vim keymap — coverage checklist

Enumerated from vim's own documentation (`:help motion.txt`, 1403 lines), not
written from memory. Each motion's exclusive/inclusive/linewise class is taken
from the doc text, because that class is what makes operators correct: `dw` and
`de` differ only in it.

Runtime docs resolve via `nvim_get_runtime_file` — a hardcoded path is wrong
because a distro AppImage mounts them at an ephemeral location that disappears
when that nvim process exits. To read the file, copy it out from inside the same
nvim session that resolves it.

Expected state for every case below comes from `tools/vim_oracle.sh`, never from
recollection. Harness A covers text/cursor/mode; undo granularity requires
harness B.

Status: `x` implemented and oracle-checked, ` ` not yet.

The case tables in `src/motion_test.odin` (single-line) and
`src/motion_ml_test.odin` (multi-line) hold nvim's own answers and are
regenerated by `make motions` from `tools/*_cases.tsv` — 3418 cases at the time
of writing, across motions, operators, text objects and visual mode. That count
is what `tools/check.sh` gates, and it sums the four files it names:
`motion_test`, `motion_ml_test`, `textobject_test` and `operator_test`. The
end-to-end cases are deliberately outside it, so the number will not match a
count of every `keys =` line in `src/`.

**Every case runs in one nvim.** Spawning a process per case costs ~44 ms of
startup against microseconds of real work, which made a full sweep take over two
minutes; `tools/vim_oracle_batch.lua` reuses a single instance and regenerates
everything in under a second. Two isolation leaks had to be closed for that to
be sound, and both produced plausible-looking wrong answers rather than errors:
loading the buffer is itself an undoable change (so `xxxu` undid the *setup*
until the load was made non-undoable with `undolevels = -1`), and a fresh buffer
per case accumulates swap files until nvim aborts with `E326` partway through.
Harness B still spawns its own nvim — it needs a real tty and is only used for
undo granularity.

The tests drive the **shipped dispatcher** (`src/keymap*.odin`) through
`feed_keys`, not a runner written alongside them. A test-local runner can agree
with nvim while the real dispatcher disagrees, which is the single failure this
harness exists to prevent. Multi-line cases exist as a separate corpus because a
single-line buffer cannot exercise `j`/`k`/`G`/`gg` at all, and a counted `$` has
no line to count to.

Two behaviors that must be measured rather than recalled, both found this way:

- **nvim opens a file with the cursor on the first non-blank of line 1**, not at
  column 0. Starting a test at column 0 makes every `w` case on an indented line
  disagree, and "fixing" the motion to match invents a blank-start rule vim does
  not have.
- **`'startofline'` is off by default in neovim** (it is on in vim), so `G`,
  `gg` and `<C-Home>` preserve the current column instead of moving to the first
  non-blank. `+`, `-` and `_` go to the first non-blank regardless.

## Left-right motions (`*left-right-motions*`)

- [x] `h` `<Left>` `CTRL-H` `<BS>` — [count] left, exclusive
- [x] `l` `<Right>` `<Space>` — [count] right, exclusive; fails only when it
  cannot move at all and no operator is pending (`$lx` leaves the text alone,
  `3lx` from column 0 moves two and deletes, `$dl` deletes the last character)
- [x] `0` — first character of the line, exclusive
- [x] `^` — first non-blank, exclusive, count ignored
- [x] `$` `<End>` — end of line, inclusive; [count] lines down
- [x] `g_` — last non-blank, inclusive
- [x] `g0` `g<Home>` — first character of the SCREEN line, exclusive
- [x] `g^` — first non-blank of the SCREEN line, exclusive
- [x] `g$` `g<End>` — last character of the SCREEN line, inclusive

Screen-line motions resolve against the PREVIOUS frame's `Layout_Result`, since
layer 1 owns cursor mutation but is denied font metrics. Verified at the
configuration the design cites — a 50-character line in a 20-column window with
the cursor at column 25 gives `Home`→1, `End`→50, `g0`→21, `g$`→40.

When that geometry is absent (the first frame) or known-wrong (a stale frame on
a line containing tabs, which has no arithmetic path at all), the command is
**deferred** rather than resolved against zeros or approximated.

With wrap off every buffer line is one screen line, so `g0`/`g$` collapse to
`0`/`$`. That falls out of the mapping rather than being a special case — the
wrap table itself says one row per line.
- [ ] `gm` — middle of the screen line
- [ ] `gM` — middle of the line by character count
- [x] `|` (`bar`) — to column [count], exclusive
- [x] `f{char}` — right to [count]'th occurrence, inclusive
- [x] `F{char}` — left to [count]'th occurrence, exclusive
- [x] `t{char}` — till before [count]'th occurrence, inclusive
- [x] `T{char}` — till after [count]'th occurrence, exclusive
- [x] `;` — repeat last `f`/`F`/`t`/`T`
- [x] `,` — repeat last `f`/`F`/`t`/`T` in the opposite direction

`0` vs `<Home>`: `<Home>` works like `1|` and differs from `0` when the line
starts with a tab. `g0`/`g$` are SCREEN-line ends while `0`/`$` are BUFFER-line
ends — the `g` prefix means "screen line" across both axes.

## Up-down motions (`*up-down-motions*`)

- [x] `k` `<Up>` `CTRL-P` — [count] lines upward, linewise
- [x] `j` `<Down>` `CTRL-J` `<NL>` `CTRL-N` — [count] lines downward, linewise
- [x] `gk` `g<Up>` — [count] SCREEN lines upward, exclusive
- [x] `gj` `g<Down>` — [count] SCREEN lines downward, exclusive
- [x] `x` `s` `D` `C` — delete/change shorthands
- [x] `i` `a` `I` `A` `o` `O` — insert entry
- [x] `v` `V` — visual / visual-line
- [x] `u` `CTRL-R` — undo tree navigation
- [x] `-` — [count] lines upward, on the first non-blank, linewise
- [x] `+` `CTRL-M` `<CR>` — [count] lines downward, first non-blank, linewise
- [x] `_` — [count]-1 lines downward, first non-blank, linewise
- [x] `G` — line [count], default last line, linewise
- [x] `gg` — line [count], default first line, linewise
- [ ] `<C-End>` `<C-Home>` — buffer end/start
- [ ] `N%` — to N percent of the file, linewise
- [ ] `:[range]` `:go` `:goto` `go` — ex-adjacent, out of scope

`j`/`k` move by BUFFER line, `gj`/`gk` by SCREEN line. Both must exist.

In visual mode the cursor may rest ON the newline, one past the last character,
and that is how a line break gets selected: `vll` on `"ab\ncd"` puts the cursor
at column 2 and `d` then leaves `"cd"`. `l` there fails, `j` keeps the column
past the end of the next line, and leaving visual mode -- Escape, or the `v`/`V`
toggle -- clamps the cursor back onto the last character. Switching between `v`
and `V` keeps the anchor; only entering from normal mode sets it.

## Word motions (`*word-motions*`)

- [x] `w` `<S-Right>` — [count] words forward, exclusive
- [x] `W` `<C-Right>` — [count] WORDs forward, exclusive
- [x] `e` — forward to word end, inclusive
- [x] `E` — forward to WORD end, inclusive
- [x] `b` `<S-Left>` — [count] words backward, exclusive
- [x] `B` `<C-Left>` — [count] WORDs backward, exclusive
- [x] `ge` — backward to word end, inclusive
- [x] `gE` — backward to WORD end, inclusive

A *word* is a sequence of letters/digits/underscores, or a sequence of other
non-blank characters, separated by whitespace. A *WORD* is any sequence of
non-blank characters. The distinction is the whole reason both sets exist.

## Text object motions (`*object-motions*`)

- [ ] `(` `)` — sentences
- [x] `{` `}` — [count] paragraphs backward / forward, exclusive
- [ ] `[[` `]]` `][` `[]` — sections

Sentences and sections are out of scope; each needs its own boundary rules.

`{` and `}` transcribe nvim's `findpar()`, and three of its rules contradict
intuition, each measured:

- A paragraph boundary is an EMPTY line. A line holding only spaces or tabs is
  not one: on `"one\ntwo\n\nthree\n  \nfour\nfive"`, `}` stops at line 3
  and `}}` runs to the end of the buffer, past the whitespace-only line. A form
  feed in column 1 and a line opening with one of the nroff macros in nvim's
  default `'paragraphs'`/`'sections'` (`.PP`, `.SH`, ...) are boundaries too.
  The line the motion starts on never counts, even when it is one.
- Reaching the end of the buffer lands on the LAST CHARACTER and makes the
  motion inclusive, so `d}` on the final paragraph takes it whole and leaves no
  empty line; `}` on the last line stays put, and `d}` there deletes one
  character.
- A count that runs off either end FAILS rather than clamping: `3}` on
  `"a\n\nb"` leaves the cursor where it was and `d3}` deletes nothing, while
  `2}` on the same text lands on `b`, because the count is spent at the moment
  the edge is reached.

## Text objects (`*text-objects*`)

`iw` selects the run under the cursor — a word *or* a whitespace run, since white
space between words counts as an object of its own. A newline is not a unit of
its own, though: `d2iw` on `"one\ntwo three"` removes `"one\ntwo"`, crossing the
line break within one step rather than spending one on it.

A bracket object does not require the cursor to already be inside the pair.
With the cursor before it on the same line vim still finds it — `di(` on
`"foo(bar baz)qux"` with the cursor on the `f` yields `"foo()qux"` — so the
search goes outward first and then forward to the next pair opening on the line.

- [x] `aw` `iw` `aW` `iW` — word / WORD
- [ ] `as` `is` — sentence
- [ ] `ap` `ip` — paragraph
- [x] `a(` `i(` `a[` `i[` `a{` `i{` `a<` `i<` `ab` `aB` — bracket blocks
- [x] `a"` `i"` `a'` `i'` ``a` `` ``i` `` — quoted strings
- [ ] `at` `it` — tag blocks

## Operators (`:help operator`)

- [x] `d` — delete; a charwise range spanning lines that starts within the
  indent and ends before only trailing blanks becomes linewise, for delete
  ALONE: `de` on `"a\nbb  \nccc"` leaves `"ccc"`, while `ye` there yanks the
  fragment `"a\nbb"` and `ce` keeps the line
- [x] `c` — change, one undo step (see below)
- [x] `y` — yank, into the one register described below
- [x] `x` `D` — character / to-end-of-line shorthands
- [ ] `>` `<` — shift
- [ ] `gu` `gU` `g~` — case
- [ ] `!` `=` — filter/indent

**A change is ONE undo step**, as vim's is: `cwX<Esc>` then a single `u`
restores "word here". The delete node absorbs the typing that follows and
becomes a `Replace`, the shape a visual paste already used.

This was shipped broken first, and the way it broke is worth keeping. The
obvious fusion passed every unit and corpus case while `make fuzz` reported five
undo-to-root violations. The diagnosis written down at the time -- that a
visual-mode `c` entering insert immediately was the breaking shape -- was WRONG,
and re-checking it against a node dump is what found the real cause: a Replace's
`range` names the bytes standing in the buffer right now, and the fusion
OVERWROTE that end instead of growing it. Typing `iw`, jumping the cursor to
column 0 and typing `Z` shrank the range from `0..2` to `0..1` and orphaned the
`iw`, so undo left text behind.

**The trigger is a HOST API call, not a keystroke**, which is why no
keyboard-only test on either side would have found it. A cursor jump mid insert
session is what `ed_set_cursor` does, and a host doing completion or
jump-to-error makes that call routinely -- so this was reachable in ordinary use
rather than only under a fuzzer. Confirmed against the pre-fix build through the
ABI alone: `Vc`, type `iw`, `ed_set_cursor(0,0)`, type `Z`, undo -- `"Wiw"`
instead of `"W"`.

So the end grows by what each insertion adds, and an insertion that is not
contiguous with the node ends the change rather than extending across the gap.
Both halves are load-bearing and only one is visible to the unit tests:
dropping the contiguity check leaves every test green and returns four fuzzer
violations.

## Simple changes (`:help simple-changes`)

Not motions or operators, and previously absent from this file altogether —
which is the failure a checklist exists to prevent: a reader could not tell
these were unimplemented, because they were not listed as anything. The
unchecked ones are silent no-ops, verified through the C ABI.

- [ ] `r` — replace one character
- [ ] `R` — replace mode
- [ ] `~` — toggle case of the character under the cursor
- [ ] `J` — join lines
- [ ] `S` — substitute whole line (`cc`)
- [ ] `>>` `<<` — shift the current line
- [x] `%` — jump to the matching bracket
- [ ] `.` — repeat the last change

**`.` is the largest single absence here**, and it was missing from this
checklist entirely until an integration hit it — which is the failure a
checklist exists to prevent, and the second time this file has had it. A vim
user reaches for `.` within minutes of real editing.

It is not a scope cut, and it is not hard for the reason it looks hard. The
difficulty is that a repeat needs the last change as DATA — the operator, its
count, the motion or text object, and the text typed in insert mode — which
means recording every change in a form that can be replayed rather than
replaying keystrokes. The keymap currently keeps none of that: `apply_operator`
takes a resolved range and forgets what produced it.

Until it lands, a host that needs repetition drives it from its own key
history; nothing here helps with that.

Operator + motion composes through the motion's class: an exclusive motion stops
before the end position, an inclusive one includes it, and a linewise motion
takes whole lines. Doubling the operator (`dd`, `cc`, `yy`) is linewise.

That composition is not the whole story, and the exceptions are where an
operator implementation written from intuition goes wrong. All of these are
quoted from vim's own docs and pinned by cases:

- **The two general exceptions** (`:help exclusive`, `*exclusive-linewise*`).
  If an exclusive motion ends in **column 1**, the end moves back to the end of
  the previous line and the motion becomes inclusive; if additionally the start
  was at or before the line's first non-blank, it becomes **linewise**. Without
  these, `dw` on a line's last word leaves a stray newline.
- **The `w`-with-operator rule** (`:help word`, "Another special case"). When
  `w` is used with an operator and the **last word moved over** ends a line,
  the end of that word bounds the operated text — not the first word on the next
  line. The bound is the end of that *word*, not of its line.
- **`cw` is treated like `ce` on a non-blank** (`:help word`, "Special case"),
  but only while the word extends past the cursor: on a word's last character
  `ce` runs to the next word's end while `cw` takes just that character.
- **Change and delete differ at line boundaries.** `cc` keeps an empty line to
  insert into where `dd` removes the line, and a change never extends its start
  back over leading indent — `'startofline'` applies to `d`, not `c`.
- **A motion that cannot move fails**, and a failed motion aborts the pending
  operator rather than applying it to a degenerate range. A *partial* move still
  counts: `3b` near the buffer start lands on column 0 and succeeds.
- **Counts multiply**: `2d3w` is `d6w`. Verified.

## The register (`:help registers`)

**ONE register, not twenty-six.** Every delete, change and yank writes it, and
`p`/`P` paste it; last write wins, so a `yy` after a `dd` replaces what `dd`
took. Named registers (`"ayy`), the numbered ring (`"1p`), the small-delete
register and the read-only ones are all out of scope — a second slot buys a
syntax and a lifetime question for a case that does not come up in practice.

- [x] `p` `P` — paste after / before, with a count (`3p` pastes three times)
- [x] `p` `P` over a visual selection — the selection is replaced, as one
  undo step
- [x] `y` `d` `c` `x` and friends all write the one register
- [ ] `"a`–`"z` named registers, `"0`–`"9` the numbered ring
- [ ] `:registers`

Measured against nvim, and several are not what intuition says:

- **`ddP` and `dwP` and `xP` restore the original text**, because paste-before
  puts back exactly what the delete took.
- **`xp` transposes** — the classic — because charwise paste lands AFTER the
  cursor's character and leaves the cursor on the last pasted one.
- **A linewise paste puts the cursor on the first non-blank of the first pasted
  line**, not at the column it was in.
- **A linewise register always ends with a newline**, even when it came from
  the buffer's last line, which has none. `dd` on the final line stores
  `"gamma\n"` with regtype `V`; storing the raw slice instead makes the next
  paste join two lines.
- **A change writes the register too**, so `cw` then `p` pastes what `cw`
  removed.
- **A visual `p` writes the register with what it replaced, and `P` does
  not**, so `vep` twice swaps two words while `veP` twice pastes the same
  word twice. The SELECTION's shape decides the form of the put, not the
  register's: a linewise selection takes a charwise register as one line of
  its own (`yiwjVp` on "alpha/beta/gamma" gives "alpha/alpha/gamma"), and a
  charwise selection splits its line around a linewise register (`yyjvep` on
  "alpha/beta gamma/delta" gives "alpha//alpha/ gamma/delta"). The cursor
  follows the put's form: last character of a charwise one, first non-blank
  of a linewise one.
- **An emptied buffer still has one line.** `dd` on a one-line buffer leaves an
  empty buffer, and `p` pastes BELOW that empty line -- `["", "a"]` -- while `P`
  pastes above it, `["a", ""]`. Treating the empty case as a plain insert gives
  the `P` answer for both: the same characters in the wrong order, which reads
  as correct until the blank line is noticed.

A host wiring the SYSTEM clipboard uses `ed_selection_text` with
`ed_replace_selection` / `ed_insert_at_cursor`, or writes this register through
`ed_set_register` so its own paste and `p` agree; see `ffi/README.md`.

## Scrolling (`:help scrolling`)

Cursor-moving and view-only, and the split matters: the first four are MOTIONS
and live with the cursor logic, so a host that scrolled its own view instead
left the cursor behind and a later edit acted off-screen.

- [x] `<C-d>` `<C-u>` — half a window down / up, cursor and view together
- [x] `<C-f>` `<C-b>` — a full window, less two lines of context
- [x] `<C-e>` `<C-y>` — the view alone, a line at a time
- [x] `zz` `zt` `zb` — the cursor's line to the middle / top / bottom
- [ ] `<C-d>`'s count PERSISTING as vim's `scroll` option
- [ ] `zh` `zl` and horizontal scrolling
- [ ] `scrolloff`

Measured at a 20-row window on a 40-line buffer, cursor on line 1:

    <C-d>  -> 11    half the window, plus the line it started on
    <C-f>  -> 19    a window less two, so the last two lines head the new view
    <C-u>  -> 1     clamped
    2<C-d> -> 3     a count is the DISTANCE, not a repeat

**The count does not persist.** In vim, `2<C-d>` sets the `scroll` option and a
later bare `<C-d>` moves 2. That is a stateful option this editor does not
otherwise have, and the oracle resets it between cases so no expectation
depends on it.

**`zt` and `zb` clamp where vim does not.** vim lets the last line sit at the
top of the window with blank space below — `30Gzt` on a 40-line buffer reports
topline 30. This editor clamps to `scroll_max`, the largest offset that still
shows content, which is the rule the wheel and every jump-to-line already
follow and which the ABI exposes as `ed_scroll_max`. Following vim for `zt`
alone would mean changing all of them, so the divergence is deliberate.

The view-only commands report an offset rather than applying it, because the
scroll offset lives in the HOST — two views of one buffer scroll independently.
See `ed_take_scroll_request` in `ffi/README.md`.

## Searching (`:help search-commands`)

- [x] `/` `?` — search forward / backward, sharing the `:` command line
- [x] `n` `N` — repeat, in the search's own direction or reversed
- [ ] `*` `#` — search for the word under the cursor
- [ ] `:noh` — clear the highlight (nothing highlights matches yet)

**The pattern is a LITERAL string, not a regex.** vim's regex is neither POSIX
nor PCRE, so matching vim here means implementing vim's dialect; anything less
is a third dialect that merely looks like it. Literal search is what a host's
find box does, and `ffi/README.md` says so at the boundary where a host would
otherwise assume.

Measured, and not what intuition says:

- A search that finds nothing ABORTS the rest of the typed sequence, the way a
  failed `f` does — `/zzz<CR>x` leaves the text untouched.
- `N` reverses the direction the search was ENTERED with, so after `?foo` it
  goes forward. The direction belongs to the search, not to the key.

## Ex commands (`:help ex-cmd-index`)

A deliberately small slice, not the ex language: `:w`, `:q`, `:wq`/`:x`, and
substitution. Everything else is out of scope below.

- [x] `:w` `:q` `:wq` `:x` — recognised, with `!` and an optional path, and
  reported to the host: the editor owns no file and no window
- [x] `:s/old/new/` `:%s/old/new/g` — substitute, literal pattern
- [ ] a range other than `%` — `:1,5s`, `:.,+3s`
- [ ] the `c` (confirm) and `i`/`I` flags

The separator is whatever follows `s`, so `:s#a/b#c#` works — which is what a
pattern containing a slash needs. Measured, and again not what intuition says:

- Without `g`, the FIRST match on each line is replaced, not the last.
- The cursor lands on the first non-blank of the LAST substituted line, not
  where it started.

## Out of scope

Marks, macros, named and numbered registers, and the ex language beyond the
handful above — named in the design's vim scope. The single unnamed register is
implemented; see above.
